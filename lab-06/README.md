# Лабораторна робота №6. Синхронізація потоків м'ютексами та семафорами

**Предмет:** Операційні системи  | **Група:** ІПЗ-41  | **Виконала:** Єва Якимчук

---

## 1. Мета роботи
Дослідити природу аномалій конкурентного доступу (Race Condition, стан гонитви) та втрачених оновлень у спільній пам'яті. Опанувати реалізацію взаємного виключення (Mutual Exclusion) за допомогою м'ютексів POSIX (`pthread_mutex_t`), а також дослідити використання лічильних семафорів (`sem_t`) для обмеження кількості одночасних потоків у критичній зоні.

---

## 2. Теоретичні відомості

### Механізм втраченого оновлення (Lost Update)
На рівні мови C операція `counter++` здається атомарною, проте асемблерний транслятор розбиває її на три окремі машинних інструкції:
1. `MOV eax, [counter]` — зчитування значення з оперативної пам'яті в регістр процесора;
2. `ADD eax, 1` — інкремент значення всередині ALU регістра;
3. `MOV [counter], eax` — запис обчисленого значення назад у спільну пам'ять.

Якщо перемикання контексту між потоками відбувається між інструкціями 1 і 3, обидва потоки зчитують однакове старе значення, і результат одного з інкрементів безповоротно втрачається.

## 3. Виконання завдань та аналіз результатів

### Завдання 1. Відтворення стану гонитви (`race_demo.c`)
Компіляція та багаторазовий запуск:
```bash
gcc -Wall -Wextra -pedantic -pthread -o race_demo race_demo.c
./race_demo
./race_demo
./race_demo
```
* **Отримані результати серії запусків:**
  * Запуск 1: Очікувано: 4 000 000 | Отримано: **1 842 190**
  * Запуск 2: Очікувано: 4 000 000 | Отримано: **2 105 432**
  * Запуск 3: Очікувано: 4 000 000 | Отримано: **1 976 341**
* **Пояснення:** Через хаотичне накладання циклів читання-модифікації-запису близько $50\%$ інкрементів губиться. Згідно зі стандартом ISO C (C11/C17 §5.1.2.4), одночасний доступ двох або більше потоків до однієї комірки пам'яті, коли хоча б один доступ є записом без бар'єрів синхронізації, є **невизначеною поведінкою (Undefined Behavior)**.

---

### Завдання 2. Захист критичної секції м'ютексом (`race_fixed.c`)
Компіляція та запуск:
```bash
gcc -Wall -Wextra -pedantic -pthread -o race_fixed race_fixed.c
./race_fixed
./race_fixed
```
* **Отриманий результат:**
```
Очікувано: 4000000
Отримано:  4000000
```
* **Пояснення:** Виклик `pthread_mutex_lock(&lock)` гарантує, що лише один потік одночасно може увійти до критичної секції. Усі інші потоки блокуються на черзі очікування. Тільки після виклику `pthread_mutex_unlock(&lock)` наступний потік отримує доступ. Операція `counter++` стає абсолютно неподільною для зовнішніх спостерігачів.

---

### Завдання 3. Лічильний семафор (`semaphore_demo.c`)
Компіляція та запуск:
```bash
gcc -Wall -Wextra -pedantic -pthread -o semaphore_demo semaphore_demo.c
./semaphore_demo
```
* **Результат при `MAX_ACTIVE = 2`:**
```
Потік 0 увійшов, активних: 1
Потік 1 увійшов, активних: 2
Потік 0 вийшов...
Потік 2 увійшов, активних: 2
Потік 1 вийшов...
Потік 3 увійшов, активних: 2
Максимальна кількість одночасних активних: 2 (межа 2)
```
* **Дослідження параметрів семафора:**
  * **При `MAX_ACTIVE = 1`:** Семафор поводиться подібно до м'ютекса (бінарний семафор), пропускаючи потоки суворо по одному (`максимальна кількість: 1`).
  * **При `MAX_ACTIVE = 4`:** Усі 4 потоки одночасно заходять у блок виконання без затримок (`максимальна кількість: 4`).
  * **Висновок:** Лічильний семафор виступає гнучким регулятором пулу ресурсів (наприклад, лімітування кількості одночасних з'єднань із базою даних або відкритих дескрипторів).

## 4. Відповіді на питання для захисту

1. **Що таке стан гонитви і чому результат `race_demo` не визначений за стандартом C?**
   Стан гонитви (Race Condition / Data Race) — це дефект проектування паралельної програми, за якого результат обчислень залежить від неконтрольованої послідовності та швидкості перемикання контексту між потоками. За стандартом C такий код класифікується як Undefined Behavior (UB), оскільки апаратні оптимізації процесора (Out-of-Order execution, кеші L1/L2) та оптимізації компілятора не гарантують узгодженість пам'яті між різними ядрами за відсутності бар'єрів пам'яті (Memory Barriers).

2. **Яку вимогу коректної синхронізації забезпечує м'ютекс?**
   М'ютекс забезпечує фундаментальну вимогу **взаємного виключення (Mutual Exclusion)**: у будь-який момент часу не більше ніж один потік може виконувати інструкції всередині захищеної критичної секції.

3. **Хто має розблокувати POSIX mutex після `pthread_mutex_lock`?**
   Виключно **той самий потік**, який успішно захопив цей м'ютекс. Розблокування м'ютекса іншим потоком заборонено стандартом POSIX і призводить до невизначеної поведінки (`EPERM`).

4. **Чим лічильний семафор відрізняється від м'ютекса?**
   * **Власність (Ownership):** М'ютекс має поняття володіння (розблокувати може лише власник). Семафор є простим системним лічильником: один потік може виконати `sem_wait()`, а абсолютно інший потік (або навіть обробник сигналів) — викликати `sem_post()`.
   * **Місткість:** М'ютекс має бінарний стан ($0$ або $1$). Лічильний семафор може мати довільне невід'ємне значення $N$, дозволяючи одночасний доступ кільком потокам до пулу ресурсів.

5. **Що станеться, якщо забути викликати `sem_post` у гілці після критичної секції?**
   Виникне поступове вичерпання дозволів семафора (Resource Starvation). Лічильник не повернеться до початкового значення, і згодом усі інші потоки назавжди зависнуть у стані нескінченного блокування на виклику `sem_wait()` (**Deadlock** / взаємне блокування).

У лабораторній роботі на практиці досліджено вразливість паралельних програм до стану гонитви, продемонстровано коректне використання м'ютексів для атомарного захисту критичних секцій та лічильних семафорів для обмеження пулу одночасних потоків у багатоядерному середовищі Linux.
